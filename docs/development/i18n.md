# Panel languages (i18n)

The panel shows its texts in the language of the user. The texts are **messages** in JSON
**catalogs**. The framework ships English (`en`, the source language) and Polish (`pl`). A module
ships the catalogs of its own texts, and a module can also add a language or change a text of
another module. The loader is `src/agento/framework/i18n/__init__.py`: it reads JSON only, imports
no module code, and uses no i18n library (DECISIONS.md, 2026-11-24).

For the React side (`useT`, `useErrorText`, the tests) see
[frontend.md](frontend.md#languages). For the routes and the error codes see
[panel.md](../architecture/panel.md#languages).

## Namespaces and keys

A message has an address: `<namespace>:<key>`.

| Namespace | Texts | Files |
|---|---|---|
| `ui` | the `@agento/ui` components | `src/agento/framework/i18n/ui/<tag>.json` |
| `panel` | the panel's own screens, the framework `acl.json` titles, the shared error texts | `src/agento/framework/i18n/panel/<tag>.json` |
| `<module name>` | one module | the files that the module's `i18n.json` names |

A module cannot use the name `ui` or `panel` as its namespace.

The module name is `name` of `module.json`; the directory name is used only when `module.json`
gives none. `module:validate`, the loader and the derived key `module.title` all take the name
from one function, `i18n.module_name`. So a directory `demo` whose manifest name is `panel` is
refused, and a pack targets a module by its manifest name.

The framework has two module identities, and they are the same text for every shipped module:
the manifest name (enablement in `cron`, config paths, the Config screen) and the directory name
(routes, the ACL registry and its ids, enablement in `web`). The namespace is the manifest name.
The panel gets a namespace from the server in two places. The Config screen uses the module
name of the config schema, which is the manifest name. The Roles screen uses `namespace` of the
role resources: the ACL registry knows the directory, so `web` maps it to the namespace with
the catalog snapshot (`Catalogs.namespaces`). The ACL ids keep the directory rule. A panel
descriptor (`nav.<path>`, `joblink`) names its module by a literal `id`; only a core module
ships one, and a test holds directory = manifest name = `id` for each. A credential limit text
is looked up in the namespace that is the credential scope, so a module that declares limit
texts gives its credential scope the same text as its name (`claude`, `codex`).

A key is lower snake case with dots: `config.title`, `error.NOT_FOUND`. A message is one of:

- a text with `{param}` holes: `"The password must have {min} to {max} characters."` A hole name
  is letters, digits and `_`;
- a plural object that the `count` param selects:
  `{"one": "{count} user", "other": "{count} users"}`. The categories are those of
  `Intl.PluralRules` (`zero`, `one`, `two`, `few`, `many`, `other`); `other` is necessary. Polish
  needs `one`, `few`, `many` and `other`.

## Derived keys

The English text of a manifest is the source message. Do not write it again in an `en` catalog. A
translation uses these keys:

| Manifest text | Key |
|---|---|
| `system.json` field `label` | `config.<field path>.label` |
| `system.json` field `description` | `config.<field path>.description` |
| `system.json` static option `label` | `config.<field path>.option.<value>` |
| the module's title on the Config screen | `module.title` (source: the module name in title case; only for a module with `system.json`) |
| `acl.json` leaf or operation `title` | `acl.<id>` |
| `acl.json` screen `title` | `acl.screen.<id of the screen's first leaf>` |
| panel descriptor (`panel/index.ts`) route `nav` | `nav.<route path>`, for example `nav./schedules` |
| panel descriptor `jobLink.label` | `joblink` |
| a credential limit window label of the module's harness (`LimitWindow.label`) | `limit.<label>`, for example `limit.Week`; the namespace is the credential scope |
| a fixed option of an `options_source` (`label_key`) | `config.option.<label_key>` in the `panel` namespace; the option's `label` is the English source. The other options of a source are data and show as sent |

Example: the `label` of `locale/date_format` in the `admin` module is `admin:config.locale/date_format.label`.
The options of an `options_source` field are not messages, but for an option that has a `label_key`. The labels of `tools[].fields` in
`module.json` have no key yet (ROADMAP.md).

## `i18n.json`

A module that has catalogs has an `i18n.json` file next to its `module.json`:

```json
{
  "version": 1,
  "languages": [{"tag": "de", "name": "Deutsch"}],
  "catalog":   {"en": "i18n/en.json", "pl": "i18n/pl.json"},
  "packs":     {"de": "i18n/pack/de.json"},
  "overrides": {"pl": "i18n/override/pl.json"}
}
```

| Key | Meaning |
|---|---|
| `version` | The integer `1`. Necessary (`true`, `1.0` and `"1"` are refused) |
| `languages` | languages that this module adds to the registry: `tag` (BCP 47: `de`, `pt-BR`, `zh-Hant`) and `name` (the language's own name) |
| `catalog` | the module's **own** texts, one flat file per language: `{"<key>": <message>}` |
| `packs` | translations of **other** namespaces, one nested file per language: `{"<namespace>": {"<key>": <message>}}` |
| `overrides` | the same shape as a pack, applied last: a deployment's own wording |

Every key but `version` is optional. A file path is relative, stays inside the module directory
and ends in `.json`.

## Layers

For each language the loader composes three layers. A higher layer replaces a key of a lower one:

1. `catalog` — each module's own texts;
2. `packs`;
3. `overrides`.

In one layer, when two modules write the same key, the module that is later in the dependency
order (`resolve_order`, from `sequence`) wins, and the loader logs one `i18n conflict` line. To
make an override win over another override, put the other module in your `sequence`.

A key that a language lacks falls back to the English source, so a catalog can be partial. English
itself is the manifest texts plus each module's `en` catalog; a pack or an override for `en`
changes the English wording.

## Languages

The registry is the union of the `languages` of the framework and of every enabled module. It gives
the options of `admin/locale/language` (`options_source: panel_languages`) and the language list in
the profile dialog (the user name in the panel header opens it over the current screen). A language is offered only when it is in the registry: a catalog file for a tag
that no `languages` entry names is not served.

The language of a user is the first of these that the registry has:

1. the language of the account (`user.ui_locale`), set in the profile dialog;
2. the instance language `admin/locale/language` ([admin.md](../modules/admin.md#language));
3. `en`.

## Glossary

`src/agento/framework/i18n/glossary.json` gives one word per language for each domain term. The
key is the English term. The value is a pattern for the stem of the translated word, so each
grammatical form of the word matches:

```json
{ "pl": { "lethal trifecta": "śmierteln\\p{L}* trójk", "agent view": "widok\\p{L}* agent" } }
```

`frontend/catalog.test.ts` reads it: when an English text has the term, the translated text must
match the pattern. A `{param}` hole and an identifier (`credential:list`, `artifact.launch`) are
not the term. To add a term, add one line, then run the test: it lists each text that uses a
different word. The test checks the word, not its grammatical form (RULES.md I18N-1).

## Validation and failure

`module:validate` (so `setup:upgrade` and `bin/test`) refuses a module whose `i18n.json` is not
valid: an unknown key, a wrong `version`, a tag that is not BCP 47, a path that leaves the module, a
file that is absent or not a JSON object, a namespace that is not a known module, a message that is
not a text or a plural object, a plural with no `other`, a key, a text or a language name that
UTF-8 cannot encode (a lone surrogate from a `\ud800` escape), and a translation with a `{param}`
that the English source of the same key does not have. A key with no English source in JSON takes
no `{param}` at all: the panel gives no params to `nav.<route path>`, `joblink` and `limit.<label>`,
whose English text is in the panel descriptor or in the harness code.

At run time the loader does not stop `web` for a bad catalog. It skips the bad entry or file,
logs one `i18n skip` line, and the lower layer or the English text stays. The same holds for a
file that makes a reader fail (a path with a NUL character, a link loop, JSON nested too deep, a
text that UTF-8 cannot encode): the file or the module's catalogs are skipped, the log line says
`reason=unusable file` or names the exception class, and the built-in texts and the sign-in
screen are served. A path that is not a regular file (a named pipe, a device) is not opened; its
states are in the table below.

The base module loader reads other files when `web` starts: `module.json`, `di.json`,
`events.json`, `system.json`, `data_patch.json`, `cron.json` and `app/etc/modules.json`. This
change adds one rule to it: a path that is not a regular file (a pipe, a device) is not opened
(a module whose `module.json` is not a regular file is not a module). Its failure modes are
not changed: bytes that are not UTF-8 in one of these files stop the start
(`UnicodeDecodeError`), and an `app/etc/modules.json` that is present
but is not a JSON object stops the composition (`AttributeError` for an array, a number or
`null`). A gate file with a wrong shape never means "all enabled".

The two start snapshots (the default instance language here, the display settings in
`api.display_schema`) read `config.json` and `system.json` of the `admin` module with the reader
below, not with `read_config_defaults`, and check each default against its schema: a language
default that is not a text or not a tag of the registry gives `en`, and a display default that is
not one of its field's options gives no display snapshot. Each drop writes one log line that does
not show the value. `read_config_defaults` is not changed for its other callers (the config
resolver): it follows a link, and its values go through the config schema at the point of use.

Every file that the loader and the validator read must be inside the module directory after
each link is followed (SEC-5): `i18n.json`, the files it names, `module.json` (for the name),
`system.json`, `acl.json` and the `config.json` of the `admin` module. A
link whose target is inside the directory is read.

The reader gives one of three states for each file it reads. `module:validate` has an error
only for the files that this feature owns: `i18n.json` and the catalog, pack and override files
it names. For the base manifests (`module.json`, `system.json`, `acl.json`, and the
`config.json` of the `admin` module) there is no validation error: the base readers accept a
link out of the module, so a deployment that works today stays valid. The loader serves no
derived text and no name from such a file and logs one line.

| State | Meaning | `module:validate` | loader |
|---|---|---|---|
| absent | the directory has no entry of that name | no error for `i18n.json`, `module.json`, `system.json`, `acl.json`; `file … not found` for a file that `i18n.json` names | no text, no log line (a named file: one `i18n skip` line) |
| unusable | an entry that is not a regular file inside the directory: a directory, a pipe, a device, a link with no target, a link that leaves the directory | for `i18n.json` and a file it names, an error: `… must be a regular file inside the module directory` (for a named file that links out: `path … must be relative, stay inside the module directory and end in .json`); for a base manifest, no error | no text, one `i18n skip` log line, and the path is not opened |
| data | the JSON content | the content checks | the content checks |

Content that is not JSON is also unusable for the loader (one `i18n skip` line); the validator
says `invalid JSON` for `i18n.json`. So a `module.json`, a `system.json` or an `acl.json` that
links out of the module gives no name and no panel text to the catalog, and the `i18n skip` log
line with `reason=unusable file` says so. The module directory is the directory that holds `module.json`, with its own
links followed first: for `app/code/<name>` that is a link, it is the target of the link; for a
PyPI module, it is the package directory in `site-packages` (or its mount at
`/opt/agento-src/<name>`). A hard link cannot be told from the file and is read.

The loader applies the namespace rule too: a pack or an override reaches only the namespaces of
the enabled modules, `ui` and `panel`. An entry for a module that is disabled or not installed is
not served, and the other entries of the same file are.

A log line and a validation message name a problem by its position and by identifiers (module,
layer, language tag, namespace, key, file path, param name). They never quote a message text or
another value of your files, and a name that is not identifier-shaped (letters, digits and
`_ . : / -`, at most 120 characters) shows as `<not an identifier>`.

## A catalog for your module

1. Write `i18n.json` with `catalog`, and one flat file per language.
2. Put the texts of your panel screen in `en.json`. Do not repeat `system.json` or `acl.json`
   texts there.
3. Translate: the same keys, plus the derived keys of your manifests, in `pl.json`.
4. For each refusal code of your routes add `error.<CODE>` (see
   [panel.md](../architecture/panel.md#error-codes)). Do not copy a text that the `panel`
   namespace holds (`error.generic`, `error.NOT_FOUND`, the `error.UPLOAD_*` texts): the panel
   reads `panel` when your namespace has no such key. `tests/unit/test_refusal_contract.py`
   fails when a code of a core module has no text in English and in Polish.
5. Run `bin/agento module:validate`.

`web` composes the catalogs at start. Restart `web` after you change a catalog file, and after
`module:enable` or `module:disable` of a module that has texts or languages (the registry, the
sign-in texts, the default instance language and the namespaces are parts of that one snapshot).

**Enablement rule:** a module that `app/etc/modules.json` disables by its directory name or by its manifest name gives no catalog and no language.

`web` and a CLI process take this rule from one function (`i18n.enabled_manifests`). The two
names are the same text for every shipped module.

## A language pack on PyPI

A language pack is a module with no Python: `module.json`, `i18n.json` and the pack file.

```
agento_lang_de/
  module.json            # {"name": "agento_lang_de", "sequence": [...], "tools": []}
  i18n.json              # languages: de; packs: {"de": "i18n/pack/de.json"}
  i18n/pack/de.json      # {"ui": {...}, "panel": {...}, "jira": {...}}
```

- Name each module that you translate in `sequence` only if the pack must not load without it. A
  namespace of a module that is not installed is a validation error.
- Publish it like any extension, then `uv add agento-lang-de` and
  `bin/agento module:enable agento_lang_de` ([modules guide](../modules/README.md)). Restart `web`.
- The language then shows in `admin/locale/language` and in the profile dialog. Disable the module
  and the language goes away: an account that stored it shows the instance language.

## Wheel

The built-in catalogs and every core module's `i18n.json` and `i18n/` files are package data.
`tests/check_wheel_frontend.py` fails a wheel that lacks a built-in catalog.
